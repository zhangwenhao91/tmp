[ub_scalar 测试完成 2026-09-20] UB->scalar->UB 标量中转路径性能测试结果与分析

一、测试结果（差分法，5规格 x r16/r128，恒等校验 5/5 PASS）

标量/向量路径差距：bf16 1504~2468 倍，f32 972~1223 倍。

二、瓶颈定位：标量指令发射率（issue rate），非内存带宽

证据1：每元素耗时与形状无关（16x256 和 128x256 均为 12.94ns）——纯发射率瓶颈，
      不像 DMA 随块尺寸扩展。
证据2：f32 带宽恰为 bf16 的 2 倍（0.31 vs 0.15），但元素速率相同——按
      "每元素一次 load + 一次 store" 计价，与位宽无关。
12.9ns/元素 ≈ 20 cycles（~1.6GHz），覆盖标量 load + store + 地址计算 +
三层循环控制开销。标量 ALU 无向量化、无流水重叠，为裸标量代码天花板。

三、结论

1. UB->scalar->UB 功能可行（AIV 标量 ALU 可访问 UB，恒等 PASS），但性能上
   仅适合控制流/零散数据操作；批量搬运必须走向量路径。
2. 从数据上坐实此前判断：即使 L1 标量路径在硬件上允许（实际不允许，AIC 无
   标量 ALU），~2000 倍的带宽差距也没有工程价值。标量路径彻底排除出搬运
   候选。
3. NPU 上 UB 内批量搬运唯一合理路径：向量 DMA（vld/vst，230~370GB/s）。

[l1ub_single 待上板验证 2026-09-20] L1->UB->L1 单核 AIC 版（绕开 mix 0x7bc87）

一、方案

mix 双核版多轮修复均报 0x7bc87（跨核同步问题域）。单核方案让全部指令
（MOV.L1.TO.UB / MOV.UB.TO.L1 / LOAD.L1.TO.L0A / MAD 本就是 AIC 专属）留在
单个 AIC 核执行，从根上消除跨核同步。

单核化由编译流水线完成，不改 DSL（复用原 l1ub 函数，带 gemm 消费）。
关键差异在 stage3 仅 --npu-plan-memory：
  - 无 --npu-split-scope：会给 op 打 crossCoreDeps，plan-memory 对 cbuf->ca
    的 L1->L0A 装载 copy 报 "failed to recognize single-pipe op"
  - 无 split-mix-kernel / sync-pipeline / split-dataflow：不拆核、不插
    INTRA.BLOCKI 跨核同步
  - 无 --npu-expand-ub-to-l1-nd2nz：线性 UB->L1 copy 由 cce-pipeline 直接
    lower 为 MOV.UB.TO.L1 行循环，expand 反而引入 pset.b16 谓词循环（退化）
  - stage6 ccec 不加 -cce-enable-mix

编译脚本 build_l1ub_single.sh 已重建并全量复现：10 个 .o 与已推送产物
逐字节一致（git 验证 0 个已跟踪文件被修改）。

二、NPU 机验证步骤

  cd ~/tmp && git pull
  cd bench_transfer
  python bench_run.py prep     # 生成 l1ub_single 输入（X/W1/W2）

  - 对比 ub2ub 带宽：两跳中转理论低于 UB 内向量搬运
